# Архитектура реализации

Состояние на 15 октября 2026 года. Сцена собирается воспроизводимо из `config/scene.json` и Python-компонентов. Результаты проверок и ограничения перечисляются в [отчёте реализации](IMPLEMENTATION_REPORT.md).

## Структура

```text
config/scene.json                   # fps, длительность, seed, угол, рендер
build_tower_bridge.py               # мост, материалы, сборка компонентов
scene_components/
  scenario.py                      # чистые функции расписания
  city.py                          # два берега, здания, улицы, набережные
  traffic.py                       # машины, колёса, очереди, барьеры
  river.py                         # суда, поверхность, след
  lighting.py                      # практический свет и сумерки
  finish.py                        # пешеходы и детали окружения
  cameras.py                       # камеры и монтажные маркеры
  validation.py                    # проверка сцены
  traffic_validation.py            # геометрия и движение транспорта
  render_manifest.py               # чистые проверки кеша и PNG
render_tower_bridge.py              # статика, кадры, видео, проверки
scripts/project.ps1                # команды Windows
Tower_Bridge/                      # сцена и итоговые материалы
research/render_runs/<identity>/   # локальные кадры и manifest.json
```

Папка называется `scene_components`, чтобы Windows не смешивала её с `Tower_Bridge`. Корневые команды сохраняют прежние имена. Геометрия моста остаётся в корневом генераторе; разделение компонентов не означает отдельную библиотеку для каждой детали.

## Конфигурация и время

Единый файл задаёт `version=1.0.0`, `fps=24`, `duration_seconds=60`, `seed=1894`, `opening_degrees=68`, разрешение 1920×1080, масштаб preview 25% и 16 образцов. Число кадров вычисляется как fps × длительность. Исходный сценарий размечен на 60 секунд, функции пересчитывают его на настроенную длительность.

Ось X направлена вдоль дороги, Y — вдоль речного маршрута, Z — вверх; единица сцены соответствует метру. Машины, люди, барьеры и суда получают согласованные ключи. Сцена хранит вычисленные ключевые кадры, поэтому перемотка и открытие `.blend` не требуют выполнения Python или frame-change handlers. Это постановочная анимация, а не дорожный симулятор с обратной связью.

## Рендер и воспроизводимость

Финальная анимация использует Eevee. Статика использует Cycles: доступный GPU выбирается автоматически, при его отсутствии или ошибке устройства доступен CPU. Preview использует отдельный профиль 480×270 при текущей конфигурации. Движок и поддерживаемые параметры выбираются с учётом API Blender.

Идентификатор кеша включает SHA-256 сцены, конфигурации, скрипта рендера и кода манифеста, профиль, fps, число кадров, фактический размер и версию Blender. Несовместимая сборка получает другую папку. PNG проверяется по подписи, CRC всех блоков, IEND и полной распаковке пикселей. Перед кодированием обязательны все кадры и одинаковые размеры.

Кодирование сохраняет хеш MP4, его размер, fps, число кадров, разрешение и идентичность входов. VideoCheck проверяет идентичность и декодирует семь фаз. Упаковка повторно сверяет хеши и требует эти проверки, основные пять изображений и отчёт проверки сцены. Finalize должен предшествовать рендеру: повторное сохранение меняет идентичность сцены.

## Границы и проверка

Исходные ресурсы процедурные; сторонние FBX/GLB не требуются. Ручные изменения `.blend` следует сохранять отдельно или переносить в генератор: Build перезаписывает результат. Вода использует художественное движение поверхности и следа, без тяжёлого fluid-cache. Сумерки меняют общий и практический свет.

Проверки без Blender находятся в `tests/`; геометрия, зазоры и камера проверяются в Blender. Визуальная проверка всего монтажа и итогового видео остаётся самостоятельным условием A01–A12. Экспорт в Unity относится к E05 после основной версии.
